Step 3 · Your credential

You need one credential in .env. Open whichever of these describes you — and ignore the other one completely.

I have a Claude subscription Most people. Pro, Max or Team.

Run this on your own machine, never inside the container. It needs Claude Code installed locally — npm install -g @anthropic-ai/claude-code — and it opens a browser for you to sign in. It then prints a long-lived token.

On your own machinehost terminal
claude setup-token

The value it prints starts sk-ant-oat01-. Paste it into .env after CLAUDE_CODE_OAUTH_TOKEN= and leave ANTHROPIC_API_KEY commented out.

I have an Anthropic API key From console.anthropic.com. Billed per token.

Create one at console.anthropic.com if you do not have it yet. There is nothing to install and nothing to run.

The key starts sk-ant-api03-. Uncomment ANTHROPIC_API_KEY in .env, paste it there, and leave CLAUDE_CODE_OAUTH_TOKEN empty.

The two are not interchangeable and they look almost identical — both start sk-ant-, both run to about 108 characters. Only the prefix tells them apart, and putting one on the other's line fails silently: .env looks right, all six checks pass, and Claude asks you to log in anyway. Check 4 tests the prefix so that it fails loudly instead. Either value is a credential: .env is gitignored, and it must never be pasted into a message or a screenshot.

Why Windows gets a second question

On Windows, "do you have Docker?" is not enough of a question. Docker Desktop runs either Linux containers or Windows containers, and it cannot do both at once. Every image the standard check uses is a Linux image, so running it in Windows-container mode fails at the build step — and it used to blame your network while doing it.

Both checks now notice when you have run the wrong one and point you at the other, so a wrong guess costs you one command. But it is faster to just ask.

The first check clones the app for you. The application you spend the day on lives in its own repository, and check 1 clones it into app/ — so there is no second git clone to remember. That folder is where all your work happens, and it is what ./checkpoint.sh moves between checkpoints. If you see no checkpoints published yet beside that check, nothing is wrong: the ladder is published one rung at a time.

What could go wrong, and how to fix it

The check stops at the first failure and prints what went wrong and what to do about it, so you are never reading a stack trace. Every failure it can report is below, quoted the way it appears on your screen — find yours, open it, and do the one thing it says.

Detailed output from every step is kept in .verify-logs/, one file per check. You should not need it — the FAIL block names the cause — but when a fix below says "read the log", that is where it is.

Check 1the 'git' command was not found on your PATH

git is one of the three things this workshop needs on your own machine — the other two are Docker and Claude Code. Install it from git-scm.com/downloads, then re-run the check. Installing Git for Windows is also what gives you Git Bash, which is the shell the whole setup expects.

Check 1app/ exists but is not a git clone

You almost certainly downloaded the app as a ZIP rather than cloning it. A copy of the files is not enough: the checkpoint ladder is the git tags, so ./checkpoint.sh has nothing to move you between. The check will not delete that folder for you — you may have put work in it — so move it aside yourself and let the check clone it properly.

Check 1could not clone the workshop app

Almost always the network — a VPN or a corporate proxy is the usual culprit, and the repository itself is public. Check your connection and re-run. The full git output is in .verify-logs/01-clone.log, and it names the real cause when it is not the network.

Check 2Docker is installed but the daemon is not answering

Start Docker Desktop and wait for the whale icon to stop animating before you re-run — a daemon that is still starting looks exactly like one that is down. If you have restarted it twice and nothing changes, read the next entry: a permissions problem looks identical from here, and no amount of restarting will fix it.

Check 2you do not have permission to reach Docker / the Docker socket

The daemon is running fine. It simply will not talk to you, and restarting it cannot change that — this is the one failure that sends people into a loop they can never win. It needs an administrator once, and then a new login session: group rights are granted at logon, so nothing changes until you sign out and back in.

In an ELEVATED PowerShell, then sign out of Windows and back inhost terminal
Add-LocalGroupMember -Group docker-users -Member <your-username>
On a Linux host instead — then log out and back inhost terminal
sudo usermod -aG docker $USER
Check 3it has been sitting on check 3 for several minutes

Nothing is wrong, and this is the check earning its keep. The first run downloads the Playwright base image — roughly 2 GB — then builds three images on it: the check's own, the workshop container you spend the day inside, and the Part 3 agent. Every byte it fetches now is a byte the workshop would otherwise fetch on the day, while a room waits. The row tells you what Docker is doing and how long it has been at it (pulling 742.8MB / 1.9GB 96s). Later runs reuse it all and check 3 takes seconds. This is the reason to run the check the night before rather than at 09:05.

Check 3the container image failed to build

Almost always the network, for the same reason as above — the build has to pull that base image. Check your connection and re-run; the full build output is in .verify-logs/03-build.log. If that log mentions Windows containers rather than a download, you are in the wrong container mode — see the first entry on this list.

Check 4CLAUDE_CODE_OAUTH_TOKEN is not a setup-token value / ANTHROPIC_API_KEY is not an API key

The credential is on the wrong line. The two values are near-identical — both start sk-ant-, both around 108 characters — so this is easy to do and impossible to spot. Only the prefix tells them apart: sk-ant-oat01- comes from claude setup-token and belongs on CLAUDE_CODE_OAUTH_TOKEN; sk-ant-api03- is an API key from the Anthropic console and belongs on ANTHROPIC_API_KEY. Move it to the other line, leave the one you vacated empty, and re-run the check. This check exists because the failure is otherwise silent: without it the value is accepted, all six checks pass, and Claude asks you to log in later with nothing pointing at the cause.

Check 4the Claude Code CLI did not start inside the container

The credential is present but the container could not use it. Read .verify-logs/04-claude.log: if it mentions authentication, the token has expired or was truncated on the way into .env — re-run claude setup-token and replace the value. Check there is no stray quote or line break around it.

Check 5port 5173 is already in use — this is the port the workshop needs

Check 5 deliberately claims the port the workshop itself runs on, not a spare one, so a pass means the day will work rather than merely that some port was free. 5173 is Vite's default, so the usual culprit is another project of yours already running. If you have the workshop stack up from earlier, that is what is holding it: docker compose -f docker-compose.workshop.yml down. Otherwise move the workshop to another port — put it in .env and it is picked up by the check and the stack, so every other command in this guide stays exactly as written.

Check 6Playwright reported success but screenshots/verify.png was not written

The browser rendered the page; the container then could not write the file back out to your machine. That is a Docker file-sharing permission, not a browser problem. In Docker Desktop, check this folder is shared: Settings → Resources → File Sharing.

Check 6the headless browser could not render and capture the page

Read .verify-logs/06-screenshot.log and re-run. This one is rare, and on a machine where checks 1–5 passed it is usually transient — the site had not finished starting. If it fails twice with the same error, that is the point to ask rather than keep re-running.

When to stop and ask

There is a right moment to stop debugging this yourself, and it is earlier than most people think.

  1. Read the FAIL block first. The check stops at the first failure and prints the cause and the fix. It is not a stack trace — it is written to be acted on.
  2. Re-run once. A daemon that was still starting, or a download that dropped, passes on the second run. Once.
  3. Same failure twice? Stop. Re-running a third time will not change the answer, and this is the moment people lose an evening. Everything needed to diagnose it is already on disk.
  4. Ask us, with the report attached. Come straight to the workshop team — reply to whoever sent you this guide, and send verify-report.txt with it. That file is written next to the script on every run and says exactly which check failed and why, so attaching it is the difference between an answer in minutes and a conversation over several messages.
Never send us your .env, your token, or your API key — not in a message, not in a screenshot, not to a facilitator, and we will never ask for them. verify-report.txt is written to be safe to share: it reports whether a credential was found, never what it is. If you have already pasted a token somewhere, run claude setup-token again to replace it.
On the day itself, just raise your hand. One of us will come to you — that is what we are there for, and it is always faster than working at it alone. Do not spend the first exercise fixing your setup — the workshop is built so that falling behind never locks you out: ./checkpoint.sh puts you exactly where the room is, and nothing you have written is discarded when it does.
