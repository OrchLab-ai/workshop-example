Three windows, one command each. Do this once at the start of the workshop and leave all three open — every activity assumes it.

Three terminals

Open three terminal windows before you start and keep all three open all day. Almost every confusion about where a command goes is really a confusion about which of these you are in.

Now switch Docker to Linux containers

The environment check runs in Windows-container mode. The workshop does not — it needs Linux containers, because every workshop image is Linux, and the workshop stack will not start — Docker reports no matching manifest for windows — until you switch. Do it before anything else.

  1. Right-click the Docker whale in the system tray and choose Switch to Linux containers…
  2. Wait for Docker to restart, then check: docker info --format '{{.OSType}}' must print linux.
What switching actually does

Docker Desktop on Windows has two separate engines — one for Windows containers, one for Linux containers — and only one is active at a time. Switching stops the Windows engine and starts the Linux one (it runs inside WSL 2 or a small Hyper-V VM). Your docker commands then talk to the Linux engine. Nothing is converted, copied or removed.

Why it is safe

Each engine keeps its own images, containers and volumes on disk. While you are in Linux mode your Windows images, containers and volumes are hidden, not deleted — docker ps -a and docker images just stop listing them. The one thing that happens: any Windows container that is running when you switch is stopped, so stop anything you care about first. The first switch can take a minute, and may ask you to install WSL 2 if it is not already there.

Switching back after the workshop

Same menu: right-click the whale and choose Switch to Windows containers… Everything you had is listed again exactly as you left it. Containers that were stopped by the switch do not restart on their own — start them again as you normally would. You can switch back and forth as often as you like.

About that flag. --dangerously-skip-permissions turns off every approval prompt — the deck calls it YOLO mode, and on its own it is exactly as reckless as it sounds. What makes it reasonable here is the layer underneath it: this window is a shell inside the container, with its own filesystem and its own network, and nothing Claude does in it can reach the rest of your machine. That is the isolation the Levels of Safety slide puts first, and it is the only reason the speed is worth having. Do not take the flag home, where nothing is containing it.

The first start of the day takes a few minutes, and only the first. The container installs the app's dependencies before it can serve anything. ./workshop/up.sh is the reason step 1 is not a plain docker compose up -d: compose would report the container started — true within seconds — and hand you back a prompt while the app was still minutes away, so opening the URL then looks broken when it is merely early. The script waits, prints each phase as it happens, and tells you READY when the site actually answers. If it fails it says so, and names the log to read.

Reading the badges

Every command block in this guide carries the badge of the window it belongs in: host terminal, work terminal or claude terminal. There is nothing to work out — match the badge to the window and run it there. A web address carries your browser instead: open it there, not in a terminal.

The badges used to say your machine and in the container, which named the two container shells identically. That answered the question nobody gets wrong and stayed silent on the one that costs something: the Claude terminal is the one where exiting to run a quick command throws away the conversation.

You are ready when http://localhost:5173 loads in your browser and you have a claude prompt waiting in terminal 3.
